# V2 第十四点反思题

## 核对范围

- 需求来源：`E:\ai\exam4\exam-v4-v2-async-event-driven-observability.md` 第十四点。
- 回答对象：`E:\work\aiExam-v2` 异步导入、Outbox、批量处理、错误明细、Trace 和监控设计。

## 1. 为什么 V2 下单导入链路不能继续采用同步阻塞方式？什么时候同步反而更简单可靠？

V2 导入链路需要处理 10,000 行甚至更高规模的数据，单次请求内完成解析、规则校验、SKU 主数据查询、重复校验、数据库写入和错误明细落库，会受到 HTTP 超时、Serverless 执行时长、数据库连接占用和浏览器等待体验的共同限制。同步阻塞还缺少任务进度、批次恢复、行级错误分页、Trace 和慢批次定位能力，一旦中途失败，用户很难判断是全部失败、部分成功还是可以恢复重试。

同步方式在小数据量、延迟稳定、单事务能完整覆盖业务一致性、用户确实需要立即拿到最终结果时更简单可靠。例如几十行以内的配置导入、只读预校验、一次性表单提交，使用同步请求可以减少任务表、队列、Worker 和补偿逻辑的复杂度。

## 2. 处理单元变大或变小，会分别带来什么影响？

处理单元变大时，Outbox 消息数量、数据库提交次数和 Worker 调度开销会下降，批量查询和批量写入的吞吐通常更好。但它也会增加单批内存占用、锁持有时间、失败重试成本和尾部延迟；一个批次失败时，受影响的行数更多，错误定位也更粗。

处理单元变小时，进度反馈更细，失败隔离更好，重试成本更低，也更利于多 Worker 公平消费。但消息数量、状态更新次数、Trace/监控记录量和数据库往返次数会上升，过小会让调度开销吞掉批量写入收益。V2 默认 `IMPORT_BATCH_SIZE=1000` 是在吞吐、重试粒度和前端可观测性之间取平衡。

## 3. 如果吞吐目标从 10,000 单/分钟提升到 50,000 单/分钟，最先成为瓶颈的是 Worker、Redis 队列还是数据库写入？你会如何扩展？

最可能先成为瓶颈的是数据库写入，其次才是 Worker CPU 或队列吞吐。Worker 可以横向扩容，队列通常擅长承载短消息调度；但 `shipments` 批量 UPSERT、错误明细写入、批次状态更新、Trace 和性能日志都会集中写主库，主库连接数、索引维护、事务日志和唯一约束冲突会先限制吞吐。

扩展时应先用监控确认瓶颈位置，再按顺序处理：优化批量 UPSERT 和索引，减少无必要的逐行写入；将导入行写入 staging 表后用集合 SQL 合并；为大表做分区或冷热归档；控制连接池和 Worker 并发，避免把数据库打满；把 Trace/监控写入降采样或异步化；必要时拆出专用写入服务或按租户/仓库分片。SKU 查询可用只读缓存或本地快照降低读压力，但最终导入结果仍要保护主库写入能力。

## 4. 如果队列消息重复投递，为什么“业务幂等”比“消息只投递一次”更重要？

分布式队列很难在所有故障场景下保证真正只投递一次。典型情况是 Worker 已经完成数据库写入，但在确认消息前进程崩溃，队列只能再次投递；如果业务侧没有幂等保护，重复投递会造成重复运单、重复错误明细或重复计数。

业务幂等把正确性放在数据库和业务约束上：批次用 `task_id + unit_id` 定位，运单用 `external_code + sku_code` 做 UPSERT，错误明细在重跑批次前清理当前单元，任务统计从批次聚合刷新而不是累加。这样即使消息重复投递，也只会重复执行同一个收敛操作，不会破坏最终结果。

## 5. 如果某个处理单元中有部分行失败，你认为应该整体回滚还是成功行先入库？为什么？

V2 导入更适合成功行先入库，失败行写入错误明细并让任务进入部分成功状态。导入文件中的行通常是相互独立的业务记录，若 10,000 行中只有几十行 SKU 或必填字段错误，整体回滚会阻塞大量有效数据，也不利于用户按错误明细修正后重传。

整体回滚只适合系统性错误，例如数据库 schema 不兼容、批次事务无法保证一致性、解析规则损坏导致整批字段错位、或者下游依赖处于不可判断状态。对于普通行级校验失败，应保留成功结果、记录失败原因、支持分页排障，并通过 Trace 和监控标记该任务为 `partial_success`。

## 6. 错误明细中需要保留原始值，但手机号和地址属于敏感信息，你如何平衡排障效率和数据安全？

错误明细应满足“能定位问题”而不是“完整暴露个人信息”。前端展示和普通接口返回应默认脱敏，例如手机号只保留前后少量字符，地址只保留行政区和截断片段，外部单号和 SKU 可以保留足够定位的信息；访问完整原始值需要更高权限、审计日志和明确用途。

存储侧可以采用字段级加密、最小化保留、按任务归档清理和权限隔离。排障时优先提供行号、字段名、错误码、规则版本、脱敏原值和 trace id；确实需要恢复完整手机号或地址时，通过受控后台查询、短期授权和审计记录处理。这样既能定位解析和校验问题，也避免把敏感信息扩散到日志、截图或监控系统。

## 7. 如果 Outbox 表持续增长到千万级，你会如何清理、归档和设计索引？

Outbox 应区分热数据和历史数据。热表只保留 `pending`、可重试 `failed` 和近期 `sent` 记录；已发送且超过保留期的记录按时间分批迁移到归档表或对象存储，再小批量删除，避免长事务和全表 vacuum 压力。无法恢复的消息进入 dead letter 区域，保留错误原因和人工处理状态。

索引上，消费路径需要覆盖 `status + next_retry_at + created_at`，聚合排查需要 `aggregate_id`，历史归档需要 `created_at`。千万级以后建议按月份或日期分区，热分区只承载近期消息；删除和归档按主键游标小批量推进。监控应跟踪 pending 深度、最老未发送消息年龄、失败重试次数和归档延迟。

## 8. 如果 AI 生成的解析规则导致大量字段映射错误，监控系统如何帮助快速发现是规则问题而不是数据库问题？

规则问题的信号通常出现在解析和校验阶段，而不是数据库写入阶段。监控应按规则版本、模板指纹、字段名和错误码聚合错误分布：如果某个规则上线后 `skuCode` 缺失、手机号格式错误、数量转换失败或 `E001` SKU 不存在突然暴涨，同时数据库写入耗时和连接错误没有同步上升，就应优先怀疑字段映射或规则生成质量。

Trace 可以进一步把问题定位到任务和批次：同一 trace 下解析成功但校验错误集中、`validateDuration` 正常、`insertDuration` 很低，说明数据大多没有进入写库阶段；如果是数据库问题，则会看到写入耗时上升、事务失败、连接池错误或批次重试增加。监控页面还应支持按 rule id/template fingerprint 过滤，快速回滚问题规则或切换到人工确认过的规则。
